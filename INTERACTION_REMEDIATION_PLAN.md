# План полной доработки взаимодействий Sailwind Co-op

Дата: **2026-10-03**. Статус: **план; реализация не начата**.

База для реализации: `main`, HEAD `32bc264`, plugin `0.1.6`, **Protocol 63**.
Исходный аудит — [INTERACTION_AUDIT.md](INTERACTION_AUDIT.md), выполненный ранее на рабочем
дереве поверх `648705c`; текущий коммит уже содержит те изменения якоря, карты и остальных
доменов, которые учитывались в аудите. Реестр охватывает 93 интерактивных типа, включая
35 ShipItem. Число типов не означает процент готовности.

Пользователь разрешил планировать изменения во всех слоях и механизмах. Поэтому допустимы
переработка hooks, сообщений, policy, сохранений, доменных Sync и диагностики. Это разрешение
на объём плана; приведённые ниже будущие изменения ещё не внесены.

## 1. Цель и обязательные правила

Цель: любое поддерживаемое действие гостя имеет явный путь **захват результата → применение
хостом → наблюдение остальными → сохранение/позднее подключение**, если оно меняет общий мир
или видимый объект. Личный эффект действует только на того игрока, который взаимодействовал.

1. **Хост полностью доверяет действиям клиента.** Не вводить проверки дистанции, права
   владения, стоимости, допустимости действия, диапазонов игровых значений, NaN/Infinity.
   Сохранить handshake, совпадение PlayerState.NetId с отправителем, границы индексов/null
   объектов и корректность формата пакета. Защита порядка и повторов не является проверкой
   допустимости действия. Ванильный результат захватывается у действующего игрока;
   повторный локальный прицел/кошелёк хоста не определяет результат гостя.
2. **Нет взаимодействия — нет события взаимодействия.** Начальные состояния, физика,
   готовка, погодные изменения, эхо и обновление поз передаются как состояние. Они не
   создают ControlEvent, GameplayNotice или новую запись последнего действия. Продление
   реально активного hold допустимо, но не объявляется новым действием каждый кадр.
3. Мир и свободная физика остаются на хосте. UI, камера, zoom, кошелёк и личные needs —
   локальные. Не воспроизводить методы с PlayerNeeds/GoPointer/MouseLook слепо на хосте.
4. При несовместимом изменении wire-format повышать Protocol.Version. Существующие
   MsgType не перенумеровывать; новые добавлять после текущего максимума 88. Финальные
   имена/номера назначать при реализации, проверяя реальный enum, а не резервировать здесь.
5. Unity API — только на главном потоке. В Net остаются транспорт и DTO; доменная работа —
   в Sync, установка патчей и порядок Update — в Runtime. Удалённые позы проходят через
   NetTransform; world-позиции — через CoordSpace, позиции на лодке — boat-local.
6. Каждый Harmony callback защищён PatchGuard/try-catch, включая prefix, postfix и
   вспомогательную диагностику. Remote apply не должен повторно запускать relay.
7. Каждый пакет работ оставляет собираемую версию и запись в СОСТОЯНИЕ.md: симптом →
   причина → исправление → версия протокола → реально выполненная проверка.

Рекомендуемый порядок: **T0 → T1 → T2 → T3 → T4 → T5 → T6 → T7 → T9 → T8 → T10 →
T11 → T12 → T13**. Простое закрытие handshake/NetId=0 из T12 можно выполнить сразу после
T0 отдельным изменением. Windows recovery расследуется отдельно и не маскирует ошибки
взаимодействий. T6/T7 можно делать независимо от cooking после готовности их оснований.

Сначала исправить инфраструктуру порядка, затем переносить на неё доменные результаты:
иначе новый расходник будет правильно уменьшаться и всё равно восстанавливаться старым
ItemState. В одном пакете не смешивать unrelated refactor с механикой игры.

- [ ] Хост применяет одну операцию на главном потоке и назначает revisions всем затронутым
  объектам; ответ/рассылка связывают изменения одним OperationId. Не слать «польза» и
  «расход» как несвязанные события с разными судьбами. Наблюдатель сначала связывает объекты,
  затем обновляет итоговый визуал составного результата.
- [ ] Повтор capture/пакета не повторяет Consume, Spawn, награду или additive-эффект.
  ReliableOrdered упорядочивает поток одного peer, но не заменяет учёт операций разных
  игроков и вложенных hooks. Для двух гостей порядок приёма хостом задаёт итог;
  не вводить блокировки допуска по дистанции/владельцу.
- [ ] Созданные гостем предметы получают host identity и сопоставление локальных экземпляров.
  До remap не отправлять их как другую уже существующую вещь. Source destroy и новые
  предметы одной нарезки доставлять как связанный lifecycle; состояние рецепта сохранить.
- [ ] При null/ещё не загруженной цели не подтверждать несуществующее применение. Различать
  ожидание загрузки и окончательно отсутствующий объект, сообщать технический результат.
  Partial apply не должен случайно повторить уже применённый расход при повторе операции.
  Идемпотентность каждого элемента и полный ответ нужны даже при исключении между элементами.
  Не обещать транзакционный откат произвольных Unity методов: минимизировать операции с
  побочными эффектами, предварительно связывать объекты, восстанавливать по фактическому итоговому state.
- [ ] Личные потребности, оплата, звук в интерфейсе и случайный личный эффект остаются у автора.
  У наблюдателей разрешены отдельные мировые визуалы; remote apply не вызывает PlayerNeeds.

**Приёмка:** польза и расход одинаковы у хоста и двух гостей после передачи предмета/drop,

## 17. Протокол, проверки и условия завершения

### Стратегия интеграции

Не назначать всем будущим изменениям одну версию заранее. Первая несовместимая интеграция
после 63 требует следующей версии; каждая отдельно устанавливаемая несовместимая сборка
требует своего повышения. Если несколько DTO вводятся одним завершённым пакетом, возможен
один bump этого пакета. На каждом этапе фиксировать реальную Version в коде и документации.

Для каждого нового/изменённого сообщения описать: direction, sender gate, delivery/channel,
identity, frame, revision/request acknowledgement, источник interaction/state, lifecycle и
поведение при отсутствующем объекте. ReliableOrdered разных peer и unreliable не считать
одним общим порядком. Large chart/dirt/config payload имеют chunk assembly по revision и
полный надёжный финал; потерянный preview не влияет на сохранённый результат.

### Автоматическая проверка каждого пакета реализации

```powershell
dotnet build SailwindCoop.csproj -c Release
dotnet run --project Tools/ProtocolSmoke/ProtocolSmoke.csproj -c Release
dotnet run --project Tools/RuntimeSmoke/RuntimeSmoke.csproj -c Release
```

- Release: 0 ошибок / 0 предупреждений. Проверить, что DLL установлена и игровые процессы
  перезапущены до ручной проверки. Полный smoke запускать после завершённой правки;
  расширять тесты только для существенного нового поведения.
- ProtocolSmoke: registration без перенумерации, populated round-trip всех добавленных
  полей, чужая версия, truncated/chunks, nullable/absent object representation.
- RuntimeSmoke: actual state gates/revision/request wrap, old unreliable after reliable
  final, duplicate/late ack, lifecycle tombstone/remap, составной result после повторной
  доставки, ошибка callback и сохранение readable backup. Это должны быть проверки
  поведения, а не сравнение тестовой копии алгоритма с таким же алгоритмом.
- Signature inventory текущей DLL: отсутствующий required hook должен быть виден;
  smoke/stub на Windows не доказывает успешный Harmony hook и симуляцию под Unity Mono.
- Документы UTF-8, git diff --check, сохранность чужих изменений. В СОСТОЯНИЕ.md отдельно
  указывать «реализовано», «прошёл smoke», «проверено в игре», «проверено Unity Mono».

### T13 — игровая приёмка

Основной состав: хост + гость-исполнитель + второй гость-наблюдатель. Каждое общее действие
создают по очереди хост и гость; второй наблюдатель выявляет direct-echo-only реализацию.
Потом smoke с максимальным поддерживаемым crew. Все узкие сценарии T0–T12 обязательны;
добавить к C4 IMPLEMENTATION_PLAN.md следующие сквозные группы:

| Группа | Обязательные сценарии | Что сравнивать |
|---|---|---|
| Порядок | Old pose/state после pickup/drop/consume/nail/fold/light; два запроса до ack; duplicate | Revision, holder, количество, членство, форма; старый пакет ничего не откатывает |
| Составная операция | Нарезка/эликсир/пакля/масло/свеча/ингредиент/табак | Польза + расход + lifecycle на всех машинах, без удвоения |
| Готовка | Каждый slot, insert/click/drop/pickup; кипение/копчение/порча/топливо | Связи food/slot, heat/рецепт/материалы, снятие драйверов |
| Held | Item/anchor/rope/adjuster/orb на берегу и движущейся лодке | Поза, frame, origin, длина, holder и корректный release |
| Controls | Wheel variants/Lock/Unlock, winch, reef/furl, quick-release, pump, push | Правильный boat/object, рука не перехватывается state |
| World/layout | Boat 0/1, refit confirm/cancel, дальняя лодка, отсутствующий dock | Только адресованный hull, новые controls, deferred target |
| Карта/приборы/грязь | Fold, stroke/delete, lid/page/child pose, broom/CleanFully | Общий физический/документный результат; личная камера не включается |
| Экономика/миссии | Shop/market/TraderBoat, crate/cargo/belt, catch, delivery/reward | Предметы и награда один раз, кошельки каждого личные |
| Сон/пауза | Host/guest sleep, wake, simultaneous input, join, leave инициатора | Общие часы/blackout, отсутствие зависшего timeScale |
| Session | Late join во время hold/готовки/изменённой карты; disconnect/reconnect | Правильный baseline, нет duplicates, restored vanilla physics |
| Save | Save/reload всех новых доменов, backup/recovery, loaded-world join | Состояние мира/профиля, читаемый backup, slot не изменён при отказе |
| Тишина | Минута без ввода, потом один реальный click/hold и join | Нет выдуманных событий, last-action не меняется от baseline/physics |

Для сетевых гонок использовать воспроизводимую задержку/перестановку именно между
unreliable state и reliable финалом; обычный LAN без задержки может скрыть дефект.
В логах записывать роль, object identity, RequestId/OperationId/Revision/PoseTick, frame,
source, pending/ack и техническую причину. Частый pose не превращать в две строки на объект
в секунду по умолчанию. HUD/menu публичной сборки — на английском.
