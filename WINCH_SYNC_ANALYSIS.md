# Анализ синхронизации и плавности лебёдок (ControlsSync)

Дата: 2026-11-03  
Подсистема: `Sync/ControlsSync.cs`, `Sync/ControlsRequests.cs`, `GPButtonRopeWinch`, `GPButtonSteeringWheel`

---

## 1. Симптомы и наблюдения в игре

При тестировании буфера сглаживания в сетевом режиме (2 копии) выявлены следующие проблемы:

1. **Хост взаимодействует, клиент наблюдает:**
   - Штурвал / перо руля поворачиваются **плавно и непрерывно**.
   - Все остальные лебёдки корабля (`GPButtonRopeWinch`: шкотовые, фаловые, рифовые, якорные) со стороны клиента **визуально вообще не вращаются** (их рукоятки стоят неподвижно, хотя парус рифится или натягивается).
2. **Клиент взаимодействует, хост наблюдает:**
   - Наблюдающий хост видит вращение и штурвала, и лебёдок, но **с большими дискретными рывками** (дёрганая анимация).
3. **Ранее (в более старых версиях):**
   - Всё вращалось на обоих экранах, но с постоянными «маленькими рывками» (дискретными микроступеньками частоты сети).

## 2. Анализ реализации в движке игры (Sailwind vanilla)

Декомпиляция `Assembly-CSharp.dll` показала фундаментальное различие между реализацией штурвала и лебёдок в самой игре:

### А. Штурвал (`GPButtonSteeringWheel`)
- Не хранит автономный угол поворота для отображения.
- В каждом кадре (`ExtraLateUpdate`) читает текущий угол физического пера руля (`rudder.currentAngle`), преобразует его через передаточное отношение `RudderToWheelAngle(angle)` и сам выставляет вращение объекта штурвала:
  ```csharp
  currentInput = RudderToWheelAngle(rudder.currentAngle);
  base.transform.localEulerAngles = new Vector3(currentAngle, 0f, 0f);
  ```
- **Следствие:** Перо руля (`Rudder`) — это `HingeJoint`. Если мод плавно интерполирует угол пера руля, скрипт игры на клиенте **автоматически вращает штурвал плавно без каких-либо дополнительных усилий**.

### Б. Лебёдки (`GPButtonRopeWinch`)
- В оригинальной игре вращение рукоятки лебёдки `ApplyRotation()` вызывается **исключительно** внутри блока удержания игроком:
  ```csharp
  private void Update()
  {
      if ((bool)stickyClickedBy || isClicked || ((bool)rotHandle && rotHandle.IsGrabbed()))
      {
          ...
          ApplyRotation();      // поворачивает base.transform.Rotate(...)
          GetRotationDelta();   // вычисляет deltaRotation
          DeltaToLength();      // rope.currentLength -= deltaRotation / 360f / gearRatio
          SendLengthToRope();
      }
      ...
  }
  ```
- **Следствие:** В обратную сторону (от изменения длины троса `rope.currentLength` к вращению рукоятки) механики в игре **нет**. Если игрок на данной машине не взаимодействует с лебёдкой физически, игра никогда сама не вращает её `transform`.

## 3. Исторический анализ кода мода (git log)

### Этап 1. Исходная реализация (коммит `399a549`)
- Все `GPButtonRopeWinch` были добавлены в список узлов вращения `_nodes` наряду с шарнирами `HingeJoint`:
  ```csharp
  foreach (var h in boat.GetComponentsInChildren<HingeJoint>(true))
      nodes.Add(new Node { T = h.transform, Rb = h.GetComponent<Rigidbody>() });
  foreach (var w in boat.GetComponentsInChildren<GPButtonRopeWinch>(true))
      nodes.Add(new Node { T = w.transform, Rb = null });
  ```
- Хост транслировал углы лебёдок клиенту в `ControlStateMsg`. Клиент интерполировал их через `Quaternion.Slerp`.
- **Результат того периода:** лебёдки крутились у обоих игроков с небольшими рывками (на частоте 12 Гц).

### Этап 2. Удаление лебёдок из узлов хоста (коммит `f8c3f13`)
- **Проблема того времени:** Когда клиент заканчивал крутить лебёдку, хост присылал свою «нейтральную» позу из `_nodes`, и ручка на клиенте отскакивала назад.
- **Решение в `f8c3f13`:** `GPButtonRopeWinch` был полностью исключён из `_nodes` на хосте:
  ```csharp
  // Winch cranks are intentionally not synced as transforms: rope length is the authoritative state, and host crank pose is only cosmetic.
  ```
- Одновременно в `ControlRequestMsg` (Клиент → Хост) было добавлено поле `req.WinchRotation`, чтобы хост видел, как клиент крутит ручку.
- **Результат:** Синхронизация стала строго односторонней:
  - **Хост → Клиент:** передаётся только `Lengths` (длина троса). Вращение лебёдки не передаётся. Рукоятка у клиента замерла.
  - **Клиент → Хост:** клиент шлёт `req.WinchRotation` на каждый чих ввода.

### Этап 3. Введение системы подтверждений и эпох (коммит `ac3463d`)
- Были добавлены `ControlTrack`, `RopeEpoch`, защита локально удерживаемых элементов и фильтрация эхо-пакетов.
- Однако логика лебёдок осталась асимметричной: лебёдки в `ControlStateMsg` возвращены не были.

### Этап 4. Добавление буфера плавности (коммит `40a24fb`)
- Внедрён буфер `_rotBuf` и интерполяция по тикам хоста для `_nodes` (`InterpDelayMs = 100 ms`, 20 Гц).
- Штурвал стал идеальным, так как следует за `HingeJoint` пера руля.
- Отсутствие вращения лебёдок на клиенте стало очевидным на контрасте со сглаженным рулём.

## 5. Варианты решения

### Вариант 1. Кинематический (вычисление вращения из изменения длины троса)
В игре формула изменения длины троса от угла поворота:
$$\Delta \text{Length} = -\frac{\Delta \text{Rotation}}{360^\circ \times \text{gearRatio}}$$
Следовательно:
$$\Delta \text{Rotation} = -\Delta \text{Length} \times 360^\circ \times \text{gearRatio}$$

- **Реализация:**
  - Когда клиент (или хост) получает изменение `rc.currentLength` для лебёдки, которую локальный игрок **не держит в руках**, плавно доворачивать `winch.transform` на `\Delta \text{Rotation}` (через Slerp / Rotate).
- **Плюсы:**
  - Не меняется сетевой протокол и размер пакетов.
  - Сохраняется принцип «длина троса — авторитетное состояние».
  - Работает полностью плавно в обоих направлениях.

### Вариант 2. Полноценная интерполяция вращений (сетевой)
- **Хост → Клиент:** вернуть `GPButtonRopeWinch.transform` в массив `_nodes` (или отдельный массив лебёдок), защитив их от перезаписи при локальном удержании через `ControlTrack`. Проигрывать вращение из того же буфера `_rotBuf`.
- **Клиент → Хост:** на хосте не присваивать `winch.transform.localRotation` мгновенно, а завести целевую ротацию и делать `Quaternion.Slerp` / буферизацию для `msg.WinchRotation`.
- **Плюсы:**
  - Передаётся точное физическое положение руки и ручки.
- **Минусы:**
  - Увеличивается размер пакетов `ControlStateMsg`.
  - Требует аккуратной синхронизации при перехвате управления.

### 7.2. Что в документе пропущено или неточно

#### 7.2.1. Главная скрытая проблема: приватное поле `GPButtonRopeWinch.lastAngle`

`GetRotationDelta()` вызывается **только внутри ветки удержания** и там же делает `lastAngle = num`
(isle: `num = localEulerAngles.z`, приведённое к `[-180,180)`; `deltaRotation = num - lastAngle`).
Значит `lastAngle` догоняет позу ручки **только пока игрок крутит**.

Любая внешняя запись в `winch.transform` — а хост уже делает её в `OnControlRequest` — оставляет
`lastAngle` устаревшим. Когда после этого **хост сам** возьмётся за эту лебёдку, первый же кадр
посчитает `deltaRotation = (новая поза ручки) − (поза до чужого вращения)` и запишет это в
`DeltaToLength`: `currentLength -= deltaRotation / 360 / gearRatio`.
При `gearRatio = 5` это скачок длины до `±0.5/5 = ±0.1` за один кадр (ошибка кратна 360°, но сам
`deltaRotation` в игре обрезается до `±180`). Скачок уходит и обратно клиенту в `ControlState`.

То есть **баг существует уже сейчас**, независимо от того, какой вариант решения выбирать:
после того как клиент покрутил лебёдку, первый захват этой же лебёдки хостом дёргает трос.

Следствие для любого варианта: запись в `transform` ручки **обязана** сопровождаться записью
`lastAngle` (reflection, поле приватное, как уже сделано для `GPButtonSteeringWheel.locked` в
`ControlsRequests.cs:46`). Иначе чинишь картинку и заводишь новый рассинхрон геймплея.

#### 7.2.2. Угол ручки **не** является чистой функцией длины троса

Формула из §5 верна (`Δугол = −Δдлина × 360 × gearRatio`, это буквально `DeltaToLength`), но
`currentLength` меняют не только лебёдки:

* `RopeControllerSailReef.InitialSailRollup` — корутина `currentLength -= Time.deltaTime` (скатывание
  паруса при установке);
* `RopeControllerSailReef.Update` — сброс в 0/1 при `GameState.currentlyLoading` и `GameState.justStarted`;
* `RopeControllerSailAngle.LinkedLoosen` — `currentLength += 1f - totalLength` (связанные тросы:
  ослабление одного меняет длину другого);
* рефит/смена парусов (`ShipyardRefitSync`), реконнект, `Resync`.

Поэтому «просто интегрировать Δдлину» даёт фабрикованное вращение в этих случаях (редко и косметически,
но одинаково на всех машинах — рассинхрона не будет). Нужен порог: шаг длины больше ~0.25 за кадр
считать не вращением, а прыжком — принять новую длину за точку отсчёта и не крутить.

#### 7.2.3. Вариант 1 в том виде, как он описан, **не** будет «полностью плавным»

Длина приходит дискретно: `StateHz = 20` (50 мс) на хосте и `ControlHz = 12` (83 мс) в запросах клиента,
причём хост вообще молчит, пока ничего не меняется (`ChangeStream.Next`). Если ручку вести строго за
принятой длиной, получатся ровно те же ступени — просто не «рывки 12 Гц», а «ступеньки 20 Гц».
Нужен доводчик: непрерывный целевой угол + движение к нему за кадр с ограничением скорости.

Верхняя граница реальной скорости вращения (из `ApplyRotation` и `LimitInput`):
`|currentInput| ≤ 50 (100 при quick release)`, `rotation = input × dt × 1.4 × rotationSpeed × 0.75`,
т.е. ≈ `525 °/с` обычная работа и ≈ `1050 °/с` при quick release (`rotationSpeed` по умолчанию 10).
Доводчик со скоростью `~1500 °/с` догоняет пачку за 1–3 кадра и при равномерном вращении не отстаёт.

#### 7.2.4. Вариант 2 дороже и имеет три собственные ловушки

* **Объём.** `PutQuaternion` — 4 float = 16 байт. 15–25 лебёдок в `ControlStateMsg` на 20 Гц —
  5–8 КБ/с на клиента в одну сторону (плюс 16 байт на каждый `ControlRequest` уже сейчас).
  Отправка одного угла (4 байта) уменьшила бы это, но не снимает следующую проблему.
* **Разрыв ±180°.** И `Quaternion.Slerp` в буфере, и `Differs` (`Quaternion.Angle(...) > 0.05f`,
  `ControlsRequests.cs:37`) на непрерывно вращающейся ручке идут «коротким путём» и на переходе
  через ±180 разворачивают вращение назад/начинают слать пакеты каждый тик. Нужна явная размотка угла.
* **Собственная задержка.** `InterpDelayMs = 100` мс: если клиент, крутящий ручку, начнёт проигрывать
  свою же позу из буфера, ручка отстанет от руки на 100 мс, а на отпускании отскочит назад — это и есть
  механика «отскока» из f8c3f13. Защита нужна не «пока держу», а «пока мой последний `RequestId` не
  подтверждён» (`ItemStateGate.Receive` уже так и работает, `Sync/ItemStateGate.cs:48-49`), т.е. без
  доработки буфера вращение ручки снова будет воевать с рукой.

#### 7.2.5. Протокол менять не нужно

`ControlRequestMsg` уже несёт `HasWinchRotation` + `WinchRotation`, а `ControlStateMsg` — только
`Lengths`. Кинематический вариант выводит позу ручки из `Lengths` **на каждой машине локально**:
ни нового поля, ни `Protocol.Version`, ни правки `ProtocolSmoke` не требуется, а старый хост
продолжит работать, если клиент не перестанет заполнять `HasWinchRotation` (поле можно оставить
и просто игнорировать на приёме — 16 байт на запрос только во время вращения).

Дополнительный плюс: выведенный угол детерминирован от истории длины, поэтому «перехват» лебёдки
вторым игроком не даёт ни отскока, ни скачка — обе машины считают одно и то же из одного числа.

### 7.3. Уточнённый рекомендуемый вариант

**Реализовано 2026-11-03:** `Sync/ControlsWinches.cs` (Unity-часть: поза ручки, `lastAngle`),
`Sync/WinchCrank.cs` (чистая арифметика и правила в `CrankState`, покрыты RuntimeSmoke), вызовы —
`ControlsSync.Tick` (хост) и `ControlsSync.ApplyClient` (клиент); протокол и `ProtocolSmoke` не менялись.

Кинематический (вариант 1) с тремя обязательными поправками:

1. **Доводчик.** На каждую лебёдку в корабле: `target += -(length − lengthRef) × 360 × gearRatio`,
   затем экспоненциальный подход `angle += (target − angle) × (1 − e^(−20·dt))` (постоянная
   времени ≈ 50 мс, с прилипанием ниже 0.05°), и
   `transform.localRotation = rest × Quaternion.AngleAxis(angle, Vector3.forward)`
   (`rest` — поза ручки на момент привязки; игра вращает её `Rotate(Vector3.forward, …, Space.Self)`).
   **Уточнение (после проверки на числах):** ограничение *скорости* доводчика (`MoveTowards` на
   `1500 °/с`) шаг 20 Гц не сглаживает — шаг 10–25° закрывается за один кадр, и ручка всё равно
   дёргается на частоте сети. Нужен именно фильтр по положению: тогда каждый кадр двигает ручку на
   часть остатка, а платой становится отставание ≈ скорости × 50 мс (18° при 360 °/с, ~50° при
   быстром сбросе).
2. **Защита удержания + `lastAngle`.** Пока ручка в руке локального игрока (`Grabbed(rotHandle)` /
   `HeldButton()` / `IsLocalRopeHeld`) — не вести её, а накапливать собственный угол из `DeltaAngle`
   по кадрам и держать `lengthRef` равным текущей длине. После каждой записи в `transform` —
   писать `lastAngle` (reflection) нормализованным значением `localEulerAngles.z`.
3. **Порог прыжка.** `|Δдлина| > 0.25` за кадр — не вращение (rollup, `LinkedLoosen`, загрузка,
   рефит): принять позу как есть и обнулить накопление.

Место вызова — без нового `SyncStep`:

* хост: в `ControlsSync.Tick` сразу после `RefreshNodes()` (до отправки и до раннего `return`
  по таймеру; через `BoatContexts` это автоматически накрывает все лодки флота);
* клиент: в `ControlsSync.ApplyClient` после `ForwardLocalRopeChanges` — входящие длины этого кадра
  уже применены (`Net.PollEvents` идёт раньше в `CoopBehaviour.Update`).

Новый код — отдельный partial `Sync/ControlsWinches.cs` (массивы `_crankAngle/_crankTarget/_crankLenRef/
_crankRest/_crankZLast/_crankRope`, сброс в `RefreshNodes` и `Clear`,`FieldInfo` на `lastAngle`).
`_winches` и `_ropes` индексируются разными перечислениями, поэтому нужен массив `_crankRope[i] =
Array.IndexOf(_ropes, winch.rope)` (`FindWinchForRope` даёт только первую лебёдку для троса).

### 7.4. Что проверить в игре после реализации

1. Хост крутит шкот, клиент смотрит: плавно в обе стороны, без ступеней; остановка без хвоста.
2. Клиент крутит: у хоста плавно; у клиента собственная ручка идёт за рукой без резинки.
3. Quick release (Run при вращении на ослабление): быстрый «выстрел» ручки у обоих, без телепорта.
4. **Регресс на 7.2.1:** клиент крутит лебёдку на 180–360°, затем **хост** берёт её и крутит —
   длина троса не должна прыгать.

6. Две лодки в сцене: ручки каждой считаются независимо.
7. Клиент без сессии и переходы роль/лодка (`RefreshNodes`): без исключений в `LogOutput.log`.

Ограничение подхода (принять осознанно): углы на двух машинах совпадают с точностью до истории длины,
а не «байт в байт»; при смене парусов, когда сама игра пишет длину не от лебёдки, ручка может один раз
дёрнуться. Геймплей не задет: ручка ни на что не влияет, авторитетна только `currentLength`.
